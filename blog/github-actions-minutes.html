GitHub Actions 额度一个月用完两次：发版里跑得最快的那个 job 最贵

9 月里两次发版都卡在了最后一步，原因是组织的 Actions 额度用完了。把账单拆开一看，一次发版 77% 的钱花在只跑了 3 分半钟的 macOS 构建上。这篇讲怎么查到的、改了什么、放弃了什么，以及怎么提前看到自己的额度。

要点速览
  • 9 月 14 日和 28 日，两次发版的最后一步「零步骤失败」。原因只写在 check run 的注解里，运行日志里什么都没有。
  • 私有仓库的「每月 N 分钟」实际按美元扣：N 乘以 Linux 单价。macOS 一分钟的价钱约等于 10 分钟 Linux，Windows 约等于 1.7 分钟。
  • 每个 job 单独向上取整到分钟。改之前一次发版折合约 54 个 Linux 分钟，其中 macOS 构建占 41 个。
  • 改法：安装包 tag 只打 Windows，macOS 包改为手动补打；CI 改为手动触发，推送前在本机把检查跑完；Actions 预算设 1 美元封顶。
  • 10 月发版更勤（16 天 28 次），上半月只花了 3.96 美元，按这个节奏全月约 7.7 美元，不到额度的一半。

01发版卡在最后一步

AMEFYS 的桌面端是 Electron 写的，发版全靠 GitHub Actions：推一个 tag，工作流就会先建一个草稿 Release，然后在 Windows 和 macOS 两台机器上同时打包，最后由 publish 这一步把草稿转成正式版，并把安装包同步到 Cloudflare R2，官网的下载链接从那里取。代码放在 amefys 组织下的私有仓库，开发和发版都是我一个人。

9 月 14 日晚上发 v0.26.0-beta.4，前面几步都成功了，publish 却是红的：运行了 3 秒，一个步骤都没执行。点进去看日志，没有日志。一个没启动的 job 不会生成日志文件，网页上只有一个红叉。

失败原因最后是在 check run 的注解（annotations）里找到的，这个接口网页上不太显眼，要用 API 才查得到：

$ gh api repos/<owner>/<repo>/check-runs/<job_id>/annotations
The job was not started because recent account payments have failed
or your spending limit needs to be increased.

这句话的前半句把我带偏了一阵。我先去个人账号的账单页找付款失败的记录，那里显示用量为 0。后来查清楚了：私有仓库的 Actions 是记在仓库所属的组织头上的，个人账单页和它没关系。组织的账单页也没有欠费，也没有付款失败，真正的原因是后半句：组织本月的免费额度用完了，而支出上限默认是 0 美元，超出的部分不允许花钱，GitHub 就直接不启动新的 job。

前面的构建 job 赶在额度用完之前跑完了，安装包已经躺在草稿 Release 里，只差 publish 那两分钟。这次我按 publish 的步骤手动做了一遍：把草稿转成正式版，下载安装包传到 R2，更新下载指针，再按字节数核对官网下载到的文件。第二天额度彻底用光，连 CI 都起不来了。

02先弄清楚：额度按什么扣

GitHub 的说法是「每月含 2,000 分钟」（Free 套餐，后来组织升级到 Team 套餐，是 3,000 分钟），很容易理解成「跑满 2,000 分钟才算完」。我用组织的计费接口把 9 月的明细拉下来对了一遍，实际规则有三条。

第一条，额度其实是美元。只有私有仓库扣额度，公开仓库免费；所谓「3,000 分钟」，是按 Linux 的单价折成 18 美元来扣的，9 月账单上私有仓库的减免正好是 18.00 美元。不同机器的单价差很多：

机器每分钟单价一分钟折合 Linux 分钟
Linux（ubuntu-latest）$0.0061
Windows（windows-latest）$0.010≈ 1.7
macOS（macos-latest，3 核）$0.062≈ 10.3

第二条，每个 job 单独计费，各自向上取整到整分钟。一个只跑 3 秒的 job 也算 1 分钟。并行跑的 job 不会因为同时进行而便宜，墙钟时间看着短，账单照样一份一份加。

第三条，额度用完以后会不会继续跑，取决于预算（Budgets，旧版界面里叫 spending limit）。默认是 0 美元并且到额就停，所以免费额度一用完，所有私有仓库的工作流都会立刻停下，直到下个月重置。

分钟数会骗人计费明细里每类机器的「分钟数」是原始分钟，没乘倍率。9 月 macOS 只跑了 163 分钟，看起来是最小的一项，折成钱却是最大的一项。看账单要看金额，或者统一折成 Linux 分钟再比。

03拆开一次发版的账单

知道了规则，再看一次发版具体花了多少。我从 Actions 接口取出 9 月 14 日 v0.26.0-beta.3 每个 job 的开始和结束时间，按上面的规则算了一遍，又拿 10 月 16 日刚发的一版做对照：

改之前的那一次，墙钟时间不到 7 分钟。Windows 构建 4 分 41 秒，算 5 分钟，折合 8.3 个 Linux 分钟；macOS 构建 3 分 35 秒，是几个构建里最快的，算 4 分钟，折合 41.3 个。一次发版合计约 54 个 Linux 分钟，0.32 美元，macOS 一项就占了 77%。剩下的 setup、prepare-release 都只跑了几秒钟，但每个也照样算 1 分钟。

单看一次，0.32 美元不算什么。问题出在发版频率：9 月发版工作流一共跑了 47 次，大部分是给测试用户的 beta。月中以后 beta 已经不打 macOS 包了，全月的发版加起来仍然折合约 2,470 个 Linux 分钟，比 Free 套餐全月的额度还多。

04一个月的钱花在哪

发版只是一部分。我把 9 月和 10 月上半月所有 280 次运行的 job 都拉下来，按工作流和机器分类，统一折成 Linux 分钟：

macOS 构建占 54%，这在意料之中。排第二的 CI 有点出乎意料：它每次推送 main 都会跑一遍类型检查、lint、单元测试和构建，9 月跑了 162 次，占了 20%。其中有一部分推送只改了 docs/ 下的文档和演示页，比如 9 月 15 日那天，光是改开发日记的动画页就触发了 8 次，这些检查和文档根本没关系。

每日 BP 数据任务和品牌检查加起来不到 4%，而且是产品真正需要的，没有动。

05第二次卡住，和当天的改动

第一次卡住之后，我做了两处小改动：beta 版不再打 macOS 包，只有正式版才打；只改了文档的推送不跑 CI。组织也升级到了 Team 套餐，额度从 2,000 分钟变成 3,000 分钟。这些改动没能撑到月底。

9 月 28 日发 v0.29.1，publish 又是零步骤失败，原因和上次一样。从图 3 的累计曲线可以看到，第二次卡住时累计用量刚好越过 18 美元那条线。月中那次升级只是把线往上挪了一点，用量增长的速度几乎没变：那半个月我发了好几个正式版，每个正式版照样带着一次 macOS 构建，CI 也还在每次推送时跑。

这次我先给组织绑了付款方式，把 Actions 的预算设成 1 美元、到额就停。这样额度用完以后还能多跑一点，最多多花 1 美元，不会出现失控的账单。然后在当天做了三处改动：

改动具体做法省下的部分
tag 只打 Windows正式版和 beta 都只构建 Windows 安装包；需要 macOS 包时，在 Actions 页面手动触发同一个工作流，选 platforms=mac每次发版约 41 个 Linux 分钟
CI 改为手动触发推送 main 不再自动跑；同样的检查在推送前由我在本机跑完，没在本机验证过的改动再去页面上手动触发9 月约 661 分钟
合并小 job原来单独计算构建矩阵的 setup 并进 prepare-release；R2 之后已经没用的 CDN 预热步骤删掉每次发版 1 分钟以上

06省下来的钱，换掉了什么

这三处改动都有代价，我想把它们写清楚。

macOS 用户拿到新版本会变慢。现在 macOS 安装包要我手动补打，补打之前，官网的 macOS 下载链接一直指向最近一次补打的版本。为了不让下载链接失效，官网的下载代理改成读 R2 上一个单独的 macOS 版本指针，只有某个版本真的有 macOS 安装包时才更新它。所以只打了 Windows 的版本，不会让 macOS 的下载变成 404，Mac 用户只是停在上一个版本。这个取舍的前提是用户结构：AMEFYS 的用户大部分在 Windows 上，测试也主要在 Windows 上做。

main 分支没有了自动的质量闸。推送前不在本机跑完检查，坏代码也能进 main。我的做法是把「推送前跑全量测试、类型检查、lint 和构建」写成规矩，发版工作流里保留它自己的构建和密钥泄漏检查，坏包和带密钥的包仍然发不出去。这适合一个人维护的仓库。几个人一起提交的话，我不建议关掉 CI，宁可在 paths 过滤和缓存上下功夫。

另外还有一处容易踩的：发版工作流按 tag 设了并发组，同一个 tag 上新的运行会取消正在跑的那一次。tag 推送触发的 Windows 构建还没结束时去补打 macOS，会把 Windows 那次取消掉，所以补打一定要等前一次跑完。

10 月上半月发版的频率比 9 月还高，按这个节奏推算全月用量约 7.7 美元，是 9 月的 41%。剩下的大头是 Windows 构建和每天的数据任务，都是产品需要的部分。按现在的节奏，Team 套餐的额度用不到一半，预算里那 1 美元也没有动过。

08怎么提前看到自己的额度

这次最被动的地方是：两次都是发版失败了，我才知道额度用完。GitHub 的账单页能看到用量，但不会在你发版之前提醒你。我后来把下面几个接口接进了自己的本地运维面板，每次打开就能看到本月用了多少、按目前的节奏月底会到多少。

组织的用量明细在增强计费接口里，带 year 和 month 参数时会按天、按仓库拆开，每一行有原始分钟数、单价和金额（旧的 /orgs/<org>/settings/billing/actions 已经返回 410）：

# 按天、按仓库的用量明细：quantity 是原始分钟，grossAmount 是金额
$ gh api "/organizations/<org>/settings/billing/usage?year=2026&month=9"

# 预算：budget_amount 和 prevent_further_usage（到额是否停用）
$ gh api /organizations/<org>/settings/billing/budgets

# 一次运行里每个 job 的起止时间和机器标签，用来算单次发版的成本
$ gh api "repos/<owner>/<repo>/actions/runs/<run_id>/jobs"

算的时候记住两点：比较各项要用金额，明细里的分钟数没乘倍率；公开仓库的用量会出现在明细里，但不扣额度，要按仓库可见性分开算。我在面板上设了两道提醒：用到额度的 80% 时提示一次，开始产生费用时标红。

09几点心得

按 job 粒度算成本。CI 的账单是一个个 job 加出来的，每个 job 有自己的机器单价和取整规则，看总时长或者看分钟数都会误判。按墙钟时间看，最慢的是 Windows 构建；按钱算，最贵的是跑得最快的 macOS。

报错的前半句可能是烟雾弹。「付款失败或支出上限需要提高」，真正适用的是后半句。遇到零步骤的失败，先去注解里看原因，再去对应主体的账单页核对，私有仓库要看组织的账单。

额度用完的后果，往往比额度本身严重。这次超额实际只付了 0.72 美元，可额度一用完，整个组织的工作流全停，发版只能手工完成。所以我把预算设成一个很小但不为零的数，既能在额度用完后撑过一次发版，又不会让账单失控。

频率是成本的放大器。单次发版 0.32 美元，可 9 月发版工作流跑了 47 次，光发版一项就超过了 Free 套餐全月的额度。beta 发得勤是好事，那就让每次 beta 只做测试真正需要的事。

省钱的改动要把代价写下来。Mac 用户拿新版本变慢、main 没有自动质量闸，这些都是有意的取舍。我把原因写进了工作流文件的注释里，以后用户结构变了、或者有人加入一起开发，要回头改的时候知道当初为什么这样做。
