CloudflareWorkers缓存Supabase踩坑

Worker 前面加了缓存却没生效：Cloudflare 跨账户（O2O）缓存的坑

Worker 里写了 cacheTtl，响应头里也是 HIT，可我们这一侧一次都没缓存上。上游 supabase.co 本身也是 Cloudflare 的客户，请求经过了两个 zone。这篇讲两个 zone 串在一起时缓存到底在哪一层、怎么判断，以及三种修法各自的代价。

2026-10-16阅读约 9 分钟AMEFYS
要点速览
  • Worker 去 fetch 另一个 Cloudflare 客户的地址时，按 Cloudflare 文档的说法，会「读穿那个 zone 的缓存」。命中算在对方头上，对我们来说就是 Supabase 账单上每天约 1 GB 的 Cached Egress。
  • 上游每个响应都带 Set-Cookie: __cf_bm，而 Cloudflare 默认不缓存带 Set-Cookie 的响应，这是官方排障文档点名的 O2O 缓存失效原因。
  • 响应头里的 cf-cache-status: HIT 可能是上游 zone 的；用 curl -I 验证 R2 自定义域名，HEAD 请求每次都是 DYNAMIC，GET 才是 HIT。两个头都会误导判断。
  • 三种修法：Cache API 自己存（当天止血，按机房各存一份，用不了分层缓存）；把文件搬到自己的 R2（最终方案）；买上游的自定义域名（要付费，而且依旧是 O2O）。
  • 判断方法归结成一句：在自己那一层加一个只说自己的响应头，部署后亲眼看到 MISS 变 HIT。

01这篇和上一篇的关系

10 月 13 日，Supabase 发邮件说我们的 Cached Egress 用到了免费额度的 289%，三天内不处理就停掉整个项目。排查、升级决定、一天之内迁到 R2 的全过程写在《免费额度用到 289%》里。那篇讲的是事故怎么处理，缓存为什么失效只用了一节。

这篇只讲那一节背后的机制。我想把它单独写出来，原因是：用 Worker 给某个服务套一层自己的域名和缓存，是 Cloudflare 上很常见的做法，而很多服务本身就跑在 Cloudflare 上。只要上游也是 Cloudflare 的客户，就会碰到同样的问题，而且很难从响应头里看出来。

02O2O：一个请求经过两个 zone

Cloudflare 把每个接入的域名叫一个 zone。我们的 cdn.amefys.com 是一个 zone，Worker 跑在它上面；supabase.co 是另一个 zone，属于 Supabase 的账户。请求先经过我们的 zone，再经过他们的 zone，Cloudflare 管这种两个 zone 串联的情况叫 orange-to-orange，简称 O2O（橙色云朵是 Cloudflare 控制台里「经过代理」的图标）。官方说明里写的是：前一个 zone 的设置先生效，后一个 zone 的设置再生效。

判断上游是不是 Cloudflare 的客户很简单，直接请求一次看响应头，有 server: cloudflare 和 cf-ray 就是：

$ curl -sI https://<project>.supabase.co/storage/v1/object/public/hero-art/v1/icons/axe.png
HTTP/2 200
server: cloudflare
cf-ray: …-LAX
cf-cache-status: MISS
set-cookie: __cf_bm=…; HttpOnly; SameSite=None; Secure; Path=/; Domain=supabase.co

这是 10 月 16 日重新请求的结果，Supabase 那边的 __cf_bm 到今天也还在。这个 cookie 来自 Cloudflare 的机器人防护（Bot Management），每个响应都会带上。

03那段看起来没问题的代码

改之前的 Worker 是这么写的（已简化）。它做三件事：把 cdn.amefys.com 的路径映射到 Supabase Storage 的地址，带上 Cloudflare 的缓存参数去取，再给响应加上我们自己的 Cache-Control 和跨域头：

upstream = await fetch(targetUrl, {
  method: request.method,
  headers: upstreamHeaders,
  // Cloudflare-specific edge cache hints.
  cf: { cacheTtl: rule.cfTtl, cacheEverything: true }
})

按 Workers 文档对 cacheTtl 的描述，它会「强制 Cloudflare 缓存这个响应，不管响应上有什么头」。照字面理解，带不带 Set-Cookie 都不该有影响。文件顶上的注释也写着设计意图：靠边缘缓存把 Supabase 的出流量压到接近零。

这段代码从上线那天起，我们这一侧一次都没缓存上。前几个月流量小，Supabase 的免费额度扛得住，一直没人发现。

04缓存到底落在了哪一层

我翻了 Cloudflare 的文档，和这件事直接相关的有两处。

第一处在 Workers 的缓存说明里：fetch 会先看目标地址是不是属于另一个 zone，如果是，就读穿那个 zone 的缓存（或者那个 zone 的 Worker）；只有不属于时，才读自己 zone 的缓存。同一页还说，缓存按子请求里的主机名存，不按 Worker 自己的主机名存。也就是说，Worker 去取 supabase.co 的文件时，问的是 supabase.co 的缓存。

第二处是一篇专门的排障文档：在 O2O 的情况下，如果源站那一侧的 zone 开着机器人防护，它返回的 __cf_bm cookie 会让面向用户的这一侧跳过缓存，因为 Cloudflare 默认不缓存带 Set-Cookie 的响应。文档只描述了现象和原因，没有给解决办法，也没有提到 Workers。

两篇文档都没有直接写「O2O 下 cacheTtl 无效」。我能确定的是实测结果：Supabase 的 Cached Egress 每天涨约 1 GB，和 cdn.amefys.com 一天的总流量差不多。如果我们这一侧哪怕缓存住一部分，Supabase 那边的数字都应该明显小于总流量。换成下一节的 Cache API 之后，同一个文件第二次请求就是 X-Amefys-Cache: HIT，也印证了问题出在「谁来存」。

文档里的「不管响应上有什么头」这句话说的是缓存规则怎么定，前提是请求真的走到了你这一侧的缓存。目标地址属于另一个 zone 时，请求读的是对方的缓存，你给的参数在对方那一层能起多大作用、会不会被对方的 Set-Cookie 挡住，文档没有写清楚。遇到上游也是 Cloudflare 的情况，别从这句话推出「一定能缓存」，部署后实测。

05怎么判断是哪一层在缓存

这次排查里，有两个响应头差点让我得出错误的结论。

第一个是转发来的 cf-cache-status。当时请求 cdn.amefys.com，响应头里写着 HIT，旁边还有 sb-gateway-mode 这类 Supabase 自己的头。Worker 把上游响应头原样转发了，这个 HIT 是 Supabase 那一侧的。一个中间层如果整包转发上游的头，客户端看到的缓存状态就是上游的。

第二个是今天写这篇时碰到的。现在 cdn.amefys.com 直接绑在 R2 上，我习惯性地用 curl -I 验证，连着三次都是 DYNAMIC，看起来缓存规则失效了。换成 GET 请求，三次都是 HIT，age 也在涨：

$ curl -sI https://cdn.amefys.com/hero-art/v2/icons/axe.webp | grep cf-cache
cf-cache-status: DYNAMIC          # HEAD 请求，每次都是

$ curl -s -o /dev/null -D - https://cdn.amefys.com/hero-art/v2/icons/axe.webp | grep -E 'cf-cache|age'
age: 1380
cf-cache-status: HIT              # GET 请求

在我们这个 R2 自定义域名上，HEAD 请求每次都显示 DYNAMIC；真实用户发的都是 GET，不受影响。验证缓存时要用和用户一样的请求方法。

综合下来，我现在按这个顺序判断：

先看怎么看说明什么
上游是不是 Cloudflare 客户直接请求上游，看有没有 server: cloudflare、cf-ray有的话就是 O2O，后面几步都要做
上游有没有 Set-Cookie直接请求上游几次，看 set-cookie有 __cf_bm 一类的 cookie，默认就不会缓存
响应头是谁加的看有没有上游特有的头（如 sb-gateway-*）中间层原样转发时，cf-cache-status 可能是上游的
自己这一层命中没有在自己的代码里加一个专属头，比如 X-Amefys-Cache，连续用 GET 请求同一个地址第一次 MISS、之后 HIT，才算自己缓存住了
账单对不对得上拿上游的计费流量和自己域名的总流量比两个数差不多大，说明自己这一层几乎没挡住

06三种修法和各自的代价

能选的修法有三种：

修法做法代价我们的选择
Cache APIWorker 用 caches.default 自己存、自己取，存之前删掉 Set-Cookie缓存只在当前机房，用不了分层缓存；缓存键、失败处理、304 都得自己写10 月 14 日下午止血
搬到自己的存储文件放进自己账户下的 R2，域名直接绑 R2要迁移文件、改发布脚本；R2 出流量免费同一天傍晚切换，最终方案
用上游的自定义域名让 Supabase 直接用我们的域名对外Supabase 的自定义域名要付费；文件仍然由 Supabase 送，Cached Egress 照样计费没选

Cache API 改起来最快，当天下午就上线了。它最大的限制写在 Workers 文档里：Cache API 只作用于当前机房，和分层缓存不兼容。没有分层缓存，每个机房都要各自回源一次：

我用 10 月 11–13 日的实际数据估了一下最坏情况。那几天 cdn.amefys.com 每天的请求来自 20–31 个 Cloudflare 机房，每个机房、每个文件每天回源一次，回源量是总流量的 8.5%–12.4%。比原来的 100% 好得多，而且只和「机房数 × 文件总量」有关，用户再多也不会跟着涨。所以 Cache API 足够撑过那几天，但长期来看，这些文件本来就该放在出流量不收费、又在自己 zone 里的存储上。当天傍晚我们就迁到了 R2，cdn.amefys.com 直接绑成 R2 的自定义域名，Worker 也不再需要了。

07用 Cache API 时要自己管的几件事

换成 Cache API，等于把 Cloudflare 替你做的事接过来自己做。我们当时补了这几处，每处都配了测试，一共 8 个，其中 5 个在旧代码上会失败（代码已简化）：

// 一个路径一份缓存：去掉 query，避免 ?随机数 绕过缓存直达上游；HEAD 和 GET 共用
const key = new Request(`${url.origin}${url.pathname}`, { method: 'GET' })
const cached = await cache.match(key)
if (cached) return toClient(cached, request, rule, 'HIT')

// 回源一律用无条件 GET：存进缓存的必须是完整的响应体
const upstream = await fetch(targetUrl)
if (!upstream.ok) return passThrough(upstream)        // 失败的响应不缓存

const stored = new Headers(upstream.headers)
stored.set('Cache-Control', `public, max-age=${rule.cfTtl}`)
stored.delete('Set-Cookie')                         // 带 Set-Cookie 的响应永远不会被存
ctx.waitUntil(cache.put(key, new Response(upstream.clone().body, { headers: stored })))
return toClient(upstream, request, rule, 'MISS')

Set-Cookie 一定要删，而且删漏了不会报错。Cache API 文档写明带 Set-Cookie 的响应永远不会被缓存，建议存之前删掉这个头，或者设 Cache-Control: private=Set-Cookie；同时 put() 不管有没有存住都会正常返回。漏删的话，代码看起来每次都在存，实际一次都没存上，又回到了改之前的样子。这也是为什么要靠下面那个专属响应头来验证。

缓存键要自己定。默认按完整 URL 存，带上随便一个查询参数就是一份新缓存，等于给了别人一个绕过缓存、直接打上游的开关。我们的客户端从来不带查询参数，所以直接去掉；HEAD 请求也映射到同一个 GET 键上，只是不返回响应体。

304 要自己生成。Supabase Storage 不处理 If-None-Match，以前就是 Worker 比对 ETag 再返回 304。换成缓存以后，命中和未命中两条路都要走这个比对，否则客户端每 30 分钟轮询一次索引文件，每次都会拉一遍完整内容。

失败不能进缓存。上游偶尔返回 5xx，如果被缓存下来，这个机房的用户会在整个缓存有效期里一直拿到错误。我们只缓存 200。

还要留一个只说自己的响应头。X-Amefys-Cache 只在我们的代码里设置，HIT 和 MISS 都是这一层自己的状态，部署后连续请求三次就能确认缓存住了，用不着猜。

08几点心得

先确认上游是谁。给一个服务套 Worker 之前，先 curl 一次上游，看它是不是也在 Cloudflare 上、有没有 Set-Cookie。这两项都是「是」的话，就别指望 fetch 的缓存参数，直接按 Cache API 或者自己存储来设计。

缓存状态要看是谁报的。转发来的 cf-cache-status 可能是上游的，HEAD 请求的 DYNAMIC 也不代表 GET 不命中。自己加一个专属的头，用和用户一样的请求方法去验证。

文档没写的地方要实测。cacheTtl 的说明写着「不管响应上有什么头」，Workers 的缓存说明又写着跨 zone 的请求读的是对方的缓存，两句放在一起，O2O 下到底谁说了算，文档没有交代。这种地方部署后量一次，比读文档推理可靠。

账单是最后一道验证。响应头可以被转发、被请求方法影响，账单不会。上游的计费流量和自己域名的总流量差不多大，就说明自己这一层什么都没挡住，不管响应头写的是什么。
