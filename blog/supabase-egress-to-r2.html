SupabaseCloudflareR2成本优化事故复盘

免费额度用到 289%：一次 Supabase 超额排查，和一天之内搬到 Cloudflare R2

一封「3 天后停服」的警告邮件，把我们引到了一个藏了很久的问题：前面那层 Cloudflare 缓存，从上线那天起就没有真正生效过。罪魁祸首是一个 Set-Cookie 响应头。

2026-10-14阅读约 12 分钟AMEFYS
要点速览
  • Supabase 的 Cached Egress（缓存出流量）用到免费额度的 289%，每天还在涨约 1 GB。
  • 流量是真实新用户下载英雄图片产生的，不是被刷；但本该挡在前面的 Cloudflare 缓存一直没生效。
  • 根因：Supabase 的每个响应都带 Set-Cookie: __cf_bm，而 Cloudflare 默认不缓存带 Set-Cookie 的响应。
  • 处理：当天先升级 Pro 保住服务 → 改用 Cache API 止血 → 静态文件全部迁到 R2，域名直挂 R2，Worker 退出这条路径。
  • 结果：Supabase 不再承担任何静态文件流量；英雄图体积降了 80%；Cloudflare Worker 调用量降了约 70%。

01一封「3 天后停服」的邮件

AMEFYS 是一款 DOTA 2 桌面辅助工具，一个人开发，后端用的是 Supabase（登录、数据库、函数和文件存储），前面套了一层 Cloudflare。整个项目一直跑在两家的免费套餐上。

10 月 13 日收到 Supabase 的邮件，大意是：

你的用量在上次通知后继续大幅超出套餐额度……你现在有 3 天时间（到 10 月 16 日）采取措施，否则合理使用政策生效，你的项目将停止工作。
Cached egress (Bandwidth): 13.23 GB of 5.5 GB

「项目停止工作」指的不只是文件下载，而是整个项目返回 402：登录、数据库、翻译和语音代理全部不可用。对一个有真实用户在用的产品来说，这等于全面停服。

我当时的第一个问题很直接：为什么会用这么多缓存流量？存储里一共才几十 MB 的文件。

02先弄清楚：Cached Egress 是什么

Supabase 把出流量分成两类，各有各的额度，互不相通（官方说明）：

类型是什么我们这边主要来自
Egress（非缓存）需要回到源站处理的请求登录、数据库查询、函数调用
Cached Egress由 Supabase 自己的 CDN 从缓存直接返回的流量，主要是 Storage 里的文件英雄图片、BP 数据包、皮肤文件

控制台首页的概览卡片只显示了 Egress（1.2 / 5 GB，看起来很健康），Cached Egress 要点进 Usage 详情页才看得到：14.46 / 5 GB，289%。这也是为什么一开始看控制台会觉得「没超啊」。

问题在于：这些文件我们本来是不打算让 Supabase 来送的。下面是当时的请求路径：

当初加这层 Worker 有两个目的：一是用自己的域名（Supabase 自定义域名要付费），二是靠 Cloudflare 边缘缓存把 Supabase 的出流量压到接近零。代码注释里也是这么写的。如果缓存真的生效，Supabase 不可能送出 13 GB。

03排查：一天 1 GB 从哪来

第一步是排除「被刷了」。Cloudflare 的 GraphQL Analytics API 可以按域名、路径、客户端、IP 拆分请求和流量，cdn.amefys.com 最近 3 天的数据是：

日期（24 小时窗口）流量
10-111.05 GB
10-120.82 GB
10-131.02 GB

一天约 1 GB，乘以账期里过去的天数，正好对上账单上的 13 GB。再按客户端拆开看：

桌面端一天 1.5 万次请求，看着很多。但按 IP 一拆就清楚了：一天来自 103 个 IP，每个 IP 大约 370 次请求，正好约等于「127 个英雄 × 3 种图」下载一遍。也就是说，这是新装机的首次下载：桌面端第一次打开 BP 面板时，会把全部英雄图预下载到本地磁盘，之后都从磁盘读。本地缓存是正常的。

结论Storage 里一共只有 22 MB 文件，没有被刷，也没有客户端在反复下载。是每天几十个新用户、每人约 18 MB 的首次下载，一天下来就是 1 GB。用户在涨是好事，问题是这些流量全算到了 Supabase 头上。

04根因：缓存为什么没挡住

用 curl 连续请求同一张图，响应头里明明写着缓存命中：

$ curl -sI https://cdn.amefys.com/hero-art/v1/portraits/axe.png
HTTP/2 200
cf-cache-status: HIT
cache-control: public, max-age=31536000, immutable
sb-gateway-mode: direct
sb-gateway-version: 1

第一眼看会以为缓存是好的。但仔细看，旁边的 sb-gateway-* 是 Supabase 的响应头：我们的 Worker 把上游的响应头原样转发了。所以这个 HIT 说的是 Supabase 那一侧的 CDN 命中，恰恰就是账单上的 Cached Egress。我们自己这一侧的缓存到底有没有命中，这个头根本看不出来。

那我们这边为什么不缓存？直接请求一次 Supabase Storage：

$ curl -sI https://<project>.supabase.co/storage/v1/object/public/hero-art/v1/icons/axe.png
HTTP/2 200
cf-cache-status: HIT
cache-control: public, max-age=31536000, immutable
set-cookie: __cf_bm=…; HttpOnly; Secure; Path=/; Domain=supabase.co

每个响应都带一个 Set-Cookie: __cf_bm。这是 Cloudflare Bot Management 的 cookie：supabase.co 本身也是 Cloudflare 的客户，开了机器人防护。

Cloudflare 的官方排障文档专门写过这种情况（Bot Management cookie causes cache bypass in O2O setups）：当你的 Cloudflare zone 去请求另一个也在 Cloudflare 上的源站（所谓 orange-to-orange，O2O）时，源站那边返回的 __cf_bm cookie 会让你这一侧跳过缓存，因为 Cloudflare 默认不缓存带 Set-Cookie 的响应。

Worker 里写的 cf: { cacheTtl, cacheEverything: true } 看起来是「强制缓存」，但遇到带 Set-Cookie 的响应照样不存。这层缓存从上线那天起就没真正工作过，只是之前流量小，免费额度扛得住，一直没人发现。

心得看到 cf-cache-status: HIT 先别高兴，要分清这个头是谁加的。中间层原样转发上游响应头，会把上游的缓存状态伪装成你自己的。最好在自己的那一层加一个专门的头（比如下面的 X-Amefys-Cache），只说自己的事。

05止血：用 Cache API 把缓存放回自己这边

最快的修法是不再依赖 fetch 的缓存参数，改用 Workers 的 Cache API（caches.default）自己存、自己取，并且在存之前把 Set-Cookie 去掉。核心逻辑大概是这样（已简化）：

const cache = caches.default
// 一个路径一份缓存：忽略 query（防止 ?随机数 绕过缓存），HEAD 和 GET 共用
const key = new Request(`${url.origin}${url.pathname}`, { method: 'GET' })

const hit = await cache.match(key)
if (hit) return withHeaders(hit, { 'X-Amefys-Cache': 'HIT' })

const upstream = await fetch(storageUrl)
if (upstream.ok) {
  const headers = new Headers(upstream.headers)
  headers.delete('Set-Cookie')                      // 关键一行
  headers.set('Cache-Control', `public, max-age=${ttl}`)
  ctx.waitUntil(cache.put(key, new Response(upstream.clone().body, { headers })))
}
return withHeaders(upstream, { 'X-Amefys-Cache': 'MISS' })

失败的响应不缓存，带版本号的文件缓存一年，索引文件只缓存 5 分钟。部署后马上验证：

$ for i in 1 2 3; do curl -sI https://cdn.amefys.com/hero-art/v1/portraits/axe.png | grep x-amefys-cache; done
x-amefys-cache: MISS
x-amefys-cache: HIT
x-amefys-cache: HIT

能省多少？Cache API 的缓存按 Cloudflare 机房各自存储，所以最坏情况是：每个机房、每个文件，每天都要回源一次。用 3 天的实际数据（每天 20–31 个机房）算一下：

日期实际总流量最坏情况回源量占比
10-111.05 GB99 MB9.4%
10-120.82 GB102 MB12.4%
10-131.02 GB87 MB8.5%

更重要的是，回源量从此和用户数脱钩：它只和「机房数 × 文件总量」有关，用户翻倍也不会跟着翻倍。修复的同时补了 8 个测试，其中 5 个在旧代码上会失败，防止以后有人改回去。

06决定：先花 25 美元，保住整个项目

修好缓存不等于问题解决。这个账期已经用掉的 13 GB 退不回来，再怎么优化，账上还是 289%；而超额的后果是整个项目返回 402，不只是文件。

所以当天的决定是：先升级 Supabase Pro（每月 25 美元）保住服务，同时继续做优化，等下个账期确认用量稳定在免费额度以内，再决定要不要降回来。几个细节：

  • 确认 Spend Cap（花费上限）是开着的：开着时超出额度只会被限速，不会额外扣钱，每月最多 25 美元。
  • 不要「先升级、马上取消」：Supabase 的取消订阅等于立即降回免费版，不是到期才生效。「怕下个月忘了取消」的问题，用日历提醒解决，而不是提前点取消。
  • 升级后账期重新开始计算。Pro 的 Cached Egress 额度是 250 GB，16 号的停服风险解除。
注意免费套餐的超额处罚，波及范围往往是整个项目。一个静态文件的问题，最后差点让登录和数据库一起停掉。评估这类风险时，要按「最大波及范围」来算，而不是按出问题的那个功能来算。

07迁移：一天之内搬到 R2

Cache API 是止血，长期的问题还在：这些文件本来就不该由 Supabase 来送。Cloudflare R2 是对象存储，出流量免费，免费额度包括 10 GB 存储和每月 1000 万次读取。我们的文件一共 22 MB，前面还有缓存挡着，完全用不完。

迁移的原则是每一步都能回落，任何一步漏了都不断服务：

  1. 第 1 步　对象键 = URL 路径R2 里的对象键直接用 CDN 路径（去掉开头的 /），比如 draft/index.json、hero-art/v2/icons/axe.webp。不需要映射表，客户端的地址一个字都不用改。
  2. 第 2 步　R2 优先，Supabase 兜底Worker 先读 R2，读不到（或者 R2 出错）再回落到 Supabase。这样迁移过程中任何文件漏了，也只是走回老路。
  3. 第 3 步　复制并逐个核对把 Supabase 存储里的 423 个文件全部复制到 R2，第一轮有 2 个因为网络中断失败，补齐后按文件大小逐个核对，全部一致。
  4. 第 4 步　发布脚本改写 R2BP 数据包、英雄图镜像、拍照识别数据包、皮肤 4 个发布脚本统一改成写 R2。手动触发一次每天自动运行的数据包发布任务，确认 CI 能直接写进 R2。
  5. 第 5 步　顺手换成 WebP英雄图是 Valve 原样的 PNG/JPEG。新版本镜像转成 WebP（质量 90），放大 2 倍看也和原图没区别，总体积从 15.3 MB 降到 3.1 MB。旧版本的 PNG 保留，给已经发出去的旧客户端继续用。
  6. 第 6 步　去掉 Worker既然文件都在 R2，Worker 就只剩「加缓存头、加跨域头」两件事，而这两件事 Cloudflare 的规则就能做。于是把 cdn.amefys.com 直接绑成 R2 的自定义域名：缓存时间用缓存规则配置（索引 5 分钟、英雄图 1 年、其他带版本号的文件 30 天），跨域用响应头规则加上桶的 CORS 策略，ETag 和 304 是原生支持的。

第 6 步是唯一会造成中断的操作：解绑 Worker 的域名、再绑到 R2，中间 Cloudflare 要签发证书，大约用了 5 分钟。事后查日志，真正受影响的是北京时间 17:50–17:51 这 2 分钟里 3–4 个手机用户的大约 30 次图片请求。手机端加载图片失败会自动换成 Valve 的原图，失败结果也不会写进离线缓存，所以没有留下坏图；桌面端这段时间没有失败请求。

切换完成后，用国内家宽网络的探测节点（移动、联通、电信都有）测了一遍新的 CDN，12 个节点里 11 个正常访问。唯一失败的一次是连接被重置，和平时的零星波动在同一水平。

08顺手做掉的几件事

既然在看用量，就把 Supabase 和 Cloudflare 两边的请求都过了一遍，又找到几处能省的：

  • 对局记录上传太频繁：桌面端在对局中每 30 秒往云端写一次，进入结算界面后更是每收到一次游戏数据就写一次，占了全部 API 请求的 58%。而云端这份记录只在换新电脑登录时才会用到。改成开局一次、每 10 分钟一次、结算一次。代码审查时还发现一个边界情况：刚进结算那一刻，游戏可能还没给出胜负，因此胜负出来后会再补传一次。
  • 英雄池保存合并发送：手机上每点一下就保存一次，一个用户一天 70–110 次。改成停顿 1.5 秒后合并成一次；改动本身立刻在本地生效，页面切到后台时也会立刻补传。
  • 浏览器预检请求在边缘应答：手机网页每次调接口前，浏览器会先发一个 OPTIONS 预检。现在由我们的代理直接回答，不再转给 Supabase。
  • 挡掉扫描器：API 域名每天有不少扫描器在试 /.env、/phpinfo.php 这类路径。加了一条防火墙规则，只放行客户端真正用到的几个 API 前缀，其余在进 Worker 之前就拦掉。
  • 关掉 Early Hints：查日志时发现一批成对出现的 204/504，来自 Cloudflare 的 Early Hints 预取。它对我们的接口和页面没有任何作用，而且全部超时，直接关掉。

10几点心得

  1. 额度告警要设在超额之前，而且每一项都要有。我们的本地运维面板盯着翻译额度、构建分钟数这些，却没有盯 Cached Egress。等官方邮件来的时候，已经是 289%。
  2. 缓存要验证，不要假设。代码注释里写着「上游出流量接近零」，实际上从第一天起就没生效。加一个只属于自己这一层的响应头，部署后亲眼看到 MISS 变成 HIT 才算数。
  3. 中间层的响应头要分清来源。原样转发上游的头，会把别人的缓存状态伪装成自己的。
  4. 迁移设计成可回落的。R2 优先、Supabase 兜底，再逐个核对、最后才切流量。这样整个迁移在一天内完成，用户几乎无感。
  5. 保服务优先，钱可以晚点省。超额的后果是整个项目停服时，花 25 美元买一个月的确定性，比赶在 3 天内把所有优化都做完更稳。
