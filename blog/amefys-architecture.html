一个人 + AI，怎么搭起一款 DOTA 2 桌面工具：AMEFYS 的整体设计与技术架构

桌面端、手机网页、云端服务、每日数据管线，一个人维护。这篇从「为什么这样设计」讲起，把 AMEFYS 的整体架构拆开来看：每一块负责什么、为什么这么选、踩过哪些坑。

2026-10-15阅读约 15 分钟AMEFYS
要点速览
  • 三层结构：客户端（Electron 桌面端 + 手机网页）→ Cloudflare 边缘层（三个自有域名）→ 云服务（Supabase + 翻译 / 语音厂商）。
  • 四条设计原则：合规优先、本地优先、低成本、国内可达，再加一条贯穿始终的：一个人维护得动。
  • 游戏数据只走 Valve 官方的 GSI 接口；能在本机算的都在本机算，云端只做登录、同步、代理这些必须联网的事。
  • BP 推荐的数据每天由 CI 从公开对局重新计算，打包发到 R2；客户端下载后在本地打分，手机网页复用同一套引擎。
  • 从第一行代码到现在 161 天、829 次提交、300 多个测试文件，大部分代码由 AI 写，规矩和决策由人来定。

01AMEFYS 是什么

AMEFYS 是一款 DOTA 2 实时辅助工具，在 Windows 和 macOS 上运行，另有一个手机网页版 BP（amefys.com/bp）。它做的事大致分四类：

  • 沟通：识别游戏内的外语聊天并翻译；把你的中文翻成对方的语言发出去；队友语音转文字；快捷回复和语料包。
  • 选人：BP 阶段推荐选谁、禁谁，给出克制和搭配的理由；手机上可以拍照识别对局阵容。
  • 对局中：根据局势推荐出装、关键时间点提醒（符点、肉山等）、关键装备成型提示。
  • 对局外：对局记录和战绩、多套皮肤主题、电脑和手机之间同步设置和英雄池。

项目从 2026 年 5 月 8 日写下第一行代码，到今天是第 161 天，一共 829 次提交，界面支持中、英、俄三种语言，月活用户约 1,500。整个项目由一个人开发和运营，大部分代码由 AI 编程助手完成。

02先定原则，再谈技术

做游戏辅助工具，技术选型之前有几件事必须先想清楚。后面几乎所有的设计决定，都能追溯到下面几条原则：

原则具体是什么落到设计上
合规优先不读写游戏内存、不注入、不改网络流量、不读敌方的隐藏信息游戏数据只走 Valve 官方的 GSI 接口；聊天发送走游戏自带的聊天输入框；聊天识别只读玩家自己屏幕上看得到的文字
本地优先对局中要快、要稳，不能因为网络抖动影响体验对局记录、出装规则、BP 打分都在本机完成；网络只用于登录、同步和代理
低成本一个人的项目，固定成本要尽量接近零从各家免费额度起步：Supabase、Cloudflare、GitHub；静态资源走出流量免费的 R2
国内可达大部分用户在中国大陆所有请求都经过自有域名；海外服务前面加代理，直连作为兜底
一个人维护得动没有同事帮忙兜底自动化测试、提交前检查、把每次事故变成规矩和自动拦截
为什么把合规放第一辅助工具最大的风险不是技术难度，而是「做着做着越界了」。把边界写成原则，并且写进给 AI 的规矩里，每个新功能先过这一关，才不会在某天为了一个看起来很酷的功能，去碰不该碰的东西。

03全景图

可以把它理解成三层：最上面是用户直接接触的两个客户端；中间是 Cloudflare 上的三个自有域名，所有流量都从这里进出；最下面是真正提供能力的云服务，以及负责构建和数据计算的 CI。下面按块展开。

04桌面端：一个应用，三类窗口

为什么是 Electron

需求是「Windows 和 macOS 都要有、界面要好看、还要能叠在游戏上面」，而开发的只有一个人。Electron 用一套 Web 技术（React + TypeScript）覆盖两个平台，界面代码还能和手机网页共用一部分。代价是安装包大、内存占用高，但对「一个人做两个平台」来说，这是最划算的选择。

三类窗口，各管各的

  • 主进程：看不见，但干最多的活。接收游戏数据、写对局记录（本地 SQLite）、做文字识别、调度翻译和语音、管理更新。
  • 主窗口：设置、战绩、对局详情、BP 大面板，平时打开看看的地方。
  • 悬浮窗：透明、置顶，叠在游戏画面上，显示翻译、出装建议、提醒。它可以锁定：锁定后鼠标点击直接穿过它落到游戏里，不会误挡操作。

窗口之间不直接共享内存，而是通过 Electron 的进程间通信（IPC）交换消息；渲染进程关掉了 Node 能力，只能调用预先暴露的少量安全接口。这样即使界面层出了问题，也碰不到系统和文件。

数据从游戏流到屏幕

两路输入：

  • GSI（Game State Integration）：Valve 官方提供的接口。在游戏启动参数里打开后，Dota 2 会把玩家自己能看到的状态（英雄、物品、金钱、时间、比赛阶段）定时推送到本机的一个地址。它只给你本来就看得到的信息，这正是合规的边界。
  • 聊天识别：游戏不会通过 GSI 推送聊天内容。用户框选聊天区域后，用系统自带的文字识别（Windows 和 macOS 各有一套）读出文字，再交给翻译。

发消息这一步走过弯路。最早的做法是写游戏的配置文件、绑定按键来发送，结果发现游戏每次加载对局都会清掉这类自定义配置（这本身就是引擎的防作弊行为），在正式对局里根本发不出去。现在的做法是：把消息放到剪贴板，按游戏默认的聊天快捷键打开输入框、粘贴、发送。和玩家自己打字没有区别，代价是每条大约 1 秒。

GSI 的盲区GSI 不是万能的。比如装备还在信使身上运送的那几十秒、扔在地上的时候，它都不会报告。出装推荐如果只看 GSI，就会把你刚买的东西再推荐一遍。这类问题只能在客户端「记住」一段时间来补，而不能去读游戏内存。合规的边界，常常就是工程难度的来源。

悬浮窗：最难伺候的那个窗口

一个透明、置顶、叠在全屏游戏上的窗口，在 Windows 上会遇到各种问题：显卡驱动导致的黑角、对局之间窗口莫名消失、某些机器上 GPU 进程反复崩溃。处理方式也都偏工程化：窗口被销毁后能自动重建；GPU 连续崩溃时自动降级到软件渲染，并记住这个状态；所有崩溃都上报到 Sentry，按版本看有没有归零。

05BP 推荐：每天重算的数据，本地跑的引擎

BP 推荐是 AMEFYS 里最「数据驱动」的功能，也是架构上最有意思的一块：数据在云端算，推荐在本地跑。

  • 为什么不在服务端实时算：选人阶段只有几十秒，推荐必须马上出来，不能等网络。把统计结果打成一个约 200 KB 的数据包，客户端下载一次，之后完全本地计算，断网也能用。服务端也就不需要任何计算资源。
  • 为什么要质量闸：数据源偶尔会出问题（某天数据量骤减、字段变化）。新数据包要先和上一版比对，异常就不发布，避免一次坏数据推给所有用户。
  • 为什么永不覆盖：每个数据包的文件名都带内容哈希，发布只是更新「最新版指向哪个文件」。出了问题回滚就是改一下指向，缓存也可以放心设成永久。

同一套推荐引擎写在共享代码里，桌面端和手机网页都用它。手机网页还多了两样：拍照识别阵容（在手机本地完成识别，不上传照片）和按住说英雄名录入阵容。

06云端：Supabase 做后端，Cloudflare 做门面

Supabase：一个人的后端团队

一个人不可能从零写登录、数据库、权限和服务端函数。Supabase 把这些打包好了：

  • 登录与账号：邮箱 + 密码注册登录。
  • 数据库：用户设置、英雄池、对局记录的云端副本，用于换设备时恢复。存放用户数据的表都开了行级权限（RLS），每个用户只能读写自己的那几行。
  • 会员与额度：免费版、Pro、定制版三档，每档有哪些功能、额度多少，都写在一张配置表里。调整额度不用发版，改一行数据就生效。
  • 服务端函数：翻译代理和语音识别代理。

翻译和语音为什么要绕一道服务端？因为厂商的密钥绝不能放进客户端：安装包是可以被拆开的。客户端只带登录凭证去请求我们的函数，函数在服务端检查额度、扣减用量，再用自己的密钥调用翻译或语音厂商（翻译以火山引擎为主，另有备选）。对愿意自己折腾的用户，也保留了「填自己的密钥、直连厂商」的选项。

Cloudflare：三个域名，三种职责

域名负责什么为什么这样设计
amefys.com官网、博客、手机网页 BP；安装包下载和自动更新源静态网站托管在 GitHub Pages，前面由 Cloudflare 加速；安装包优先从 R2 下载
cdn.amefys.comBP 数据包、英雄图片、皮肤直接挂在 R2 上，出流量免费；缓存时间和跨域都用 Cloudflare 规则配置，不经过任何代码
api.amefys.com登录、数据库、函数的反向代理见下文的国内访问问题；只放行客户端用到的接口路径

api.amefys.com 的来历是一次线上事故：9 月下旬，国内部分运营商开始阻断访问 Supabase 默认域名的加密连接，用户登录直接报「网络连接失败」，翻译、语音、同步跟着全部不可用。解决办法是在 Cloudflare 上加一个反向代理，客户端优先走自己的域名，失败再回落到直连。现在国内用户的请求几乎都走代理。

cdn.amefys.com 也有一段故事：它原本由一个 Worker 转发到 Supabase 存储，结果缓存一直没生效，一个月用掉了免费额度的 289%。来龙去脉写在上一篇里，现在它已经直接挂在 R2 上了。

国内网络要尽早测开发机通常有各种网络工具，本机测永远是通的。判断国内用户能不能访问，要用国内家庭宽带的探测节点（区分移动、联通、电信），并且同时测一个已知被阻断的域名作对照组，对照组没被拦，说明这批节点的结果不可信。

07发布、更新与运维

  • 发版：本地跑完检查后打一个版本标签，GitHub Actions 自动构建 Windows 安装包并发布。macOS 包的构建成本是 Windows 的十倍左右，所以只在正式版按需构建，测试版只出 Windows。
  • 自动更新：客户端启动后和每 4 小时检查一次更新源，正式版和测试版各有一个频道。
  • 崩溃与错误：Sentry 收集崩溃和关键错误，按版本看问题是否归零。
  • 运维面板：一个只在本机运行的网页面板，汇总 Supabase、Cloudflare、GitHub 的用量和关键数字，每天看一眼。
  • 质量：321 个测试文件、3,000 多个测试用例，提交前有格式和身份检查。为了省构建额度，日常的 CI 改成了手动触发，所以推上主分支前必须在本地跑完全量测试、类型检查和构建。

08一个人 + AI 的开发方式

这个项目大部分代码是 AI 编程助手（Claude Code）写的。这不等于「让 AI 随便写」，而是一套分工：

  • 人定方向和边界：做什么、不做什么、合规红线在哪里、什么时候发版，都由人决定。
  • AI 负责实现和自查：写代码、补测试、跑检查、查线上数据。每次实现完成后，必须对照需求逐条自查，再给出结论。
  • 事故变规矩，规矩变机制：AI 每犯一次错（比如声称「已经推送」其实没有、照着原图手抄 logo 结果走样），就写成一条规矩；能自动化的，再变成提交钩子或测试，下次不用靠记性。

这部分值得单独写一篇，后面会专门展开：哪些事交给 AI 很放心，哪些地方必须自己盯着。

09回头看：几个取舍

  1. 选 Electron 没后悔。一个人覆盖两个桌面平台，再加一个共用代码的手机网页，这个效率是其他方案给不了的。安装包大、内存高是真的代价，但在可接受范围内。
  2. 托管服务优先，但要盯着额度。Supabase、Cloudflare、GitHub 的免费额度让项目前几个月几乎零成本，但免费额度一旦超出，往往会波及整个项目。用量告警应该和功能一起上线，而不是等出了事再补。
  3. 本地优先省了很多事。BP 推荐、出装规则、对局记录都在本机，服务端几乎没有计算压力，也天然不怕网络抖动。
  4. 国内网络是一等公民。海外服务的可达性会突然变化。所有请求都走自有域名，至少保证出问题时有地方可以改，而不用等用户更新客户端。
  5. 合规让很多事变难，但它是底线。不读内存，就要用更聪明的办法补 GSI 的盲区；不能用配置文件发消息，就模拟正常输入。每一个「绕路」，都是产品能长期存在的前提。
