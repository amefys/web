一个人 + AI，怎么搭起一款 DOTA 2 桌面工具：AMEFYS 的整体设计与技术架构

桌面端、手机网页、云端服务、每日数据管线，一个人维护。这篇从「为什么这样设计」讲起，把 AMEFYS 的整体架构拆开来看：每一块负责什么、为什么这么选、踩过哪些坑。

01AMEFYS 是什么

AMEFYS 是一款 DOTA 2 实时辅助工具，跑在 Windows 和 macOS 上，另外有一个手机网页版 BP（amefys.com/bp）。

它最早只做一件事：把游戏里看不懂的外语聊天翻译出来。后来陆续加了把中文翻成对方语言发出去、队友语音转文字、快捷回复和语料包。再往后有了 BP 选人推荐，告诉你选谁、禁谁、为什么；手机上还能直接拍屏幕识别阵容。对局中它会按局势推荐出装，提醒符点、肉山这类时间点，关键装备做出来时也会提示一下。对局外是战绩记录、皮肤主题，以及电脑和手机之间的设置、英雄池同步。

第一行代码写于 2026 年 5 月 8 日。到今天是第 161 天，829 次提交，界面有中、英、俄三种语言，月活用户约 1,500。开发和运营都是我一个人，大部分代码由 AI 编程助手写。

02先定原则，再谈技术

做游戏辅助工具，选技术之前有几件事得先想清楚。后来几乎每个设计决定，都能在下面这张表里找到出处。

原则具体是什么落到设计上
合规优先不读写游戏内存、不注入、不改网络流量、不读敌方的隐藏信息游戏数据只走 Valve 官方的 GSI 接口；聊天发送走游戏自带的聊天输入框；聊天识别只读玩家自己屏幕上看得到的文字
本地优先对局中要快、要稳，不能因为网络抖动影响体验对局记录、出装规则、BP 打分都在本机完成；网络只用于登录、同步和代理
低成本一个人的项目，固定成本要尽量接近零从各家免费额度起步：Supabase、Cloudflare、GitHub；静态资源走出流量免费的 R2
国内可达大部分用户在中国大陆所有请求都经过自有域名；海外服务前面加代理，直连作为兜底
一个人维护得动没有同事帮忙兜底自动化测试、提交前检查、把每次事故变成规矩和自动拦截

五条里我最看重第一条。辅助工具真正的风险在边界：做着做着，很容易为了一个看起来很酷的功能，去碰不该碰的东西。所以我把边界写成原则，也写进了给 AI 的规矩里，每个新功能先过这一关。

03全景图

整体分三层。最上面是用户直接用到的两个客户端；中间是 Cloudflare 上的三个自有域名，所有流量都从这里进出；最下面是真正干活的云服务，以及负责构建和每日数据计算的 CI。下面一块一块说。

04桌面端：一个应用，三类窗口

为什么是 Electron

需求是 Windows 和 macOS 都要有，界面要好看，还得能叠在游戏画面上面，而开发的只有我一个人。Electron 用一套 Web 技术（React + TypeScript）覆盖两个平台，界面代码还能和手机网页共用一部分。安装包大、吃内存是真实的代价，但对一个人做两个平台来说，这笔账划算。

三类窗口

主进程看不见，活却最多：接收游戏数据，往本地 SQLite 写对局记录，做文字识别，调度翻译和语音，管理更新。主窗口是平时打开看看的地方，放设置、战绩、对局详情和 BP 大面板。悬浮窗透明、置顶，叠在游戏上显示翻译、出装建议和提醒。悬浮窗可以锁定，锁定后鼠标点击会直接穿过它落到游戏里，不会挡操作。

窗口之间不共享内存，靠 Electron 的进程间通信（IPC）传消息。界面所在的渲染进程关掉了 Node 能力（nodeIntegration），只能调用 preload 里通过 contextBridge 开放的几个接口，界面层出了问题也碰不到系统和文件。

数据从游戏流到屏幕

数据有两个来源。一个是 GSI（Game State Integration），Valve 官方提供的接口：在游戏启动参数里打开后，Dota 2 会把玩家自己能看到的状态（英雄、物品、金钱、时间、比赛阶段）持续以 HTTP 请求推送到本机的一个地址。它只给你本来就看得到的东西，合规的边界也就画在这里。

另一个是屏幕上的聊天。GSI 不推送聊天内容，所以由用户框选聊天区域，再用系统自带的文字识别读出来（Windows 和 macOS 各有一套），交给翻译。

发消息这一步走过弯路。最早的做法是写游戏的配置文件、绑定按键来发，后来发现游戏每次加载对局都会清掉这类自定义配置。这是引擎自己的行为，结果就是正式对局里根本发不出去。现在的做法是把消息放进剪贴板，按游戏默认的聊天快捷键打开输入框、粘贴、发送，和玩家自己打字一样，代价是每条大约 1 秒。

GSI 也有看不见的时候装备还在信使身上运送的那几十秒、扔在地上的时候，GSI 都不会报告。出装推荐要是只看 GSI，就会把你刚买的东西再推荐一遍。这种问题只能让客户端「记住」一段时间来补，不能去读游戏内存。守合规的代价，常常就是多出来的这份工程量。

悬浮窗最难伺候

一个透明、置顶、叠在全屏游戏上的窗口，在 Windows 上会遇到各种怪事：窗口四角变黑，对局之间窗口莫名消失，某些机器上 GPU 进程反复崩溃。应对都偏工程化。窗口被销毁后会自动重建；GPU 连续崩溃时自动降到软件渲染，并记住这个状态。

05BP 推荐：每天重算的数据，本地跑的引擎

BP 推荐是 AMEFYS 里最依赖数据的功能。它的做法是数据在云端算，推荐在本地跑。

选人阶段只有几十秒，推荐必须马上出来，不能等网络。所以统计结果被打成一个约 200 KB 的数据包。客户端每天查一次有没有新包，有才下载，推荐全在本地算，断网也能用，推荐这一步完全不占服务端。

数据源偶尔会出问题，比如某天数据量骤减，或者字段变了。新数据包发布前要先和上一版比对，看着不对就不发，免得一份坏数据推给所有人。

每个数据包的文件名都带内容哈希，发布只是改一下「最新版指向哪个文件」。出了问题回滚就是改回指向，缓存也能放心设成永久。

这套推荐引擎写在共享代码里，桌面端和手机网页用的是同一份。手机网页还多了两样：拍照识别阵容（识别在手机本地完成，照片不上传），以及按住说英雄名录入阵容。

06云端：Supabase 做后端，Cloudflare 做门面

Supabase：一个人的后端团队

登录、数据库、权限、服务端函数，一个人很难从零写一遍。Supabase 把这些打包好了。账号用邮箱和密码注册登录。数据库里存用户设置、英雄池和对局记录的云端副本，换设备时用来恢复；存用户数据的表都开了行级权限（RLS），每个用户只能读写自己那几行。会员分免费版、Pro 和定制版三档，每档有哪些功能、额度多少，写在一张配置表里，调额度不用发版，改一行数据就生效。

翻译和语音识别要绕一道服务端函数，原因是厂商的密钥不能放进客户端，安装包是能被拆开的。客户端只带着登录凭证请求我们的函数，函数在服务端检查额度、记用量，再用自己的密钥去调翻译或语音厂商（翻译以火山引擎为主，另有备选）。愿意自己折腾的用户，也可以填自己的密钥直连厂商。

Cloudflare：三个域名，各管一摊

域名负责什么为什么这样设计
amefys.com官网、博客、手机网页 BP；安装包下载和自动更新源静态网站托管在 GitHub Pages，前面由 Cloudflare 加速；安装包优先从 R2 下载
cdn.amefys.comBP 数据包、英雄图片、皮肤直接挂在 R2 上，出流量免费；缓存时间和跨域都用 Cloudflare 规则配置，不经过任何代码
api.amefys.com登录、数据库、函数的反向代理见下文的国内访问问题；只放行客户端用到的接口路径

api.amefys.com 来自一次线上事故。9 月下旬起，国内部分运营商阻断了访问 Supabase 默认域名的 HTTPS 连接，用户一登录就报「网络连接失败」，翻译、语音、同步也全跟着停了。解决办法是在 Cloudflare 上架一个反向代理，客户端先走自己的域名，失败了再直连。现在国内用户的请求基本都走这个代理。

cdn.amefys.com 原来由一个 Worker 转发到 Supabase 存储，结果缓存一直没生效，一个月用掉了免费额度的 289%。来龙去脉写在上一篇，现在它已经直接挂在 R2 上。

国内能不能连上，要尽早测开发机上一般开着各种网络工具，本机测永远是通的。要判断国内用户能不能访问，得用国内家庭宽带的探测节点，分开看移动、联通、电信，同时拿一个已知被阻断的域名做对照。对照组没被拦，就说明这批节点的结果不可信。

07发布、更新与运维

发版时先在本地跑完检查，再打一个版本标签，GitHub Actions 会自动构建 Windows 安装包并发布。macOS 机器每分钟的计费是 Windows 的 6 倍多、Linux 的 10 倍多，所以 tag 只构建 Windows，macOS 包只给正式版手动补打（细节见下一篇）。客户端启动后检查一次更新，之后每 4 小时再查一次，正式版和测试版各走一个频道。

崩溃和关键错误交给 Sentry，按版本看问题有没有清零。另外有一个只在我电脑上运行的运维面板，把 Supabase、Cloudflare、GitHub 的用量和几个关键数字放在一页里，每天看一眼。

代码里有 321 个测试文件、3,000 多个测试用例，提交前会检查提交信息格式和提交身份。为了省构建额度，日常的 CI 改成了手动触发，所以推上主分支前，全量测试、类型检查和构建都得在本地跑完。

08一个人 + AI 的开发方式

这个项目大部分代码是 AI 编程助手写的，但分工很明确。做什么、不做什么、合规红线在哪、什么时候发版，由我来定。写代码、补测试、跑检查、查线上数据，交给 AI；每次做完，它要对照需求逐条自查，再给结论。

AI 也会犯错，比如声称「已经推送」其实什么都没发生，或者照着原图手抄 logo 结果走了样。每出一次这种事，我就写一条规矩；能自动化的，再做成提交钩子或测试，下次就不用靠记性了。

哪些事交给 AI 放心、哪些地方得自己盯着，后面会单独写一篇。

09回头看：几个取舍

选 Electron 没后悔。一个人覆盖两个桌面平台，再加一个共用代码的手机网页，这个效率别的方案给不了。

Supabase、Cloudflare、GitHub 的免费额度，让项目前几个月几乎零成本。但免费额度一旦超了，往往整个项目一起受影响。用量告警应该和功能一起上线，别等出了事再补。

本地优先省了很多事。BP 推荐、出装规则、对局记录都在本机，服务端几乎没有计算压力，网络抖一下也不怕。

国内用户能不能连上，要从第一天就当回事。海外服务在国内能不能访问，可能哪天就变了。所有请求都走自己的域名，至少出了问题有地方可改，不用等用户升级客户端。

合规让很多事变难了。不读内存，就得想办法补 GSI 的盲区；配置文件发不了消息，就模拟正常输入。这些绕路都省不掉，产品要长期活下去，就得守着这条线。
