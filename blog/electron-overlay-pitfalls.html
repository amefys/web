用 Electron 做游戏悬浮窗：透明窗口、焦点、全局鼠标钩子和自愈崩溃

AMEFYS 的桌面端是 Electron 写的，核心是一个盖在全屏游戏上的透明置顶悬浮窗。它把 Electron 在 Windows 上的很多角落都碰了一遍。这篇按类别整理开发以来踩过的坑，配了 10 张图和几张表，写清根因、修法，以及有没有在 Windows 实机上验证过。

01先看全貌

AMEFYS 是一款 DOTA 2 桌面工具，支持 Windows 和 macOS，当前用 Electron 41.10.7。整体架构写在另一篇里。这篇只看 Electron 本身：四类窗口，加上背后的主进程，各自踩过哪些坑。

悬浮窗的要求是互相打架的：要透明、有圆角、永远置顶；平时让鼠标穿透到游戏，需要时又要能点、能打字；而且绝不能抢走游戏的前台。下面的坑大多只在 Windows 上出现，开发机却是 Mac，这也是它们难查的原因之一。

02透明窗口：修了五次的黑角

6 月初，Windows 上悬浮窗的四个角是不透明的黑色，macOS 上正常。前四次修复都在 CSS 和窗口参数上打转，第五次才找到根因：Windows 的分层窗口有两种透明方式，逐像素透明（UpdateLayeredWindow）和整窗透明（SetLayeredWindowAttributes 加 LWA_ALPHA），两者互相排斥。

我们的悬浮窗有一个「透明度」设置，默认值 0.8 一定会被保存，所以每次启动都会调一次 setOpacity()，透明效果也就每次都被毁掉。修法是在 Windows 上完全不碰原生透明度，改用 CSS 的 opacity。后来的截图闪框、锁定暗化也都只用 CSS。这条写成了文档红线，目前还没有自动化的守卫测试。

同一个黑角，还有两个次要原因：

原因现象做法
透明窗口设了 backgroundColor哪怕写的是 #00000000，在 Windows 上也可能被当成不透明；Aero Snap 的矩形边框还会画到圆角上去掉 backgroundColor，设 thickFrame: false。社区常说，确实有影响，但不是我们的主因
皮肤的 CSS 优先级更高几个装饰皮肤后注入、选择器更具体，不透明背景铺满了窗口；外阴影只能画进四个角悬浮窗的透明规则全部加 !important，皮肤在悬浮窗里只许用内阴影
主窗口是直角，先找个对照组有台验收机上主窗口是直角，但那台机器上资源管理器和 Edge 也是直角，说明是系统的圆角整体失效了：可能是 Windows 10、显卡驱动没装、远程桌面或者虚拟机。这不是应用的 bug。主窗口的圆角由 Windows 11 在系统层裁出来，我们没有为了圆角把主窗口也做成透明的，那样会丢掉贴边分屏、原生阴影和最大化行为。

03别抢前台：焦点、置顶和任务栏

9 月有用户在对局中反馈：鼠标点到悬浮窗，游戏声音没了。DOTA 2 失去前台就静音，而悬浮窗显示时调了 setFocusable(true) 和 focus()，一显示就把前台抢走了。

这里有三件事，各由不同的 API 管，要分开想：

能获得键盘焦点吗focusable永远不可聚焦，只有打字时临时借
显示时抢前台吗show() 还是 showInactive()一律 showInactive()

置顶和任务栏状态在 Windows 上也会悄悄丢。按代码注释里的判断，全屏游戏切换或 setFocusable() 会重置置顶层级和 skipTaskbar，悬浮窗于是可能被埋到游戏下面，或者出现在任务栏里。用户在任务栏右键一关，窗口就被销毁，之后所有打开入口都静默失效。

现在每次显示都重设 setAlwaysOnTop(true, 'screen-saver')、setSkipTaskbar(true) 和 moveTop()；所有入口走同一个「确保窗口存在，没有就重建」的函数，关闭改成隐藏。「新开一局后不显示」到底是渲染进程崩了，还是全屏切换弄丢了置顶层级，还没在 Windows 日志里实锤。

04一个布尔参数背后的全局鼠标钩子

10 月 16 日有用户反馈：「我的电脑开启这个软件会隔几秒卡一下，在游戏里鼠标会卡住不动一帧，然后在下一帧恢复操作」。

悬浮窗平时让鼠标穿透到游戏，又要知道鼠标是不是移到了按钮上。我们从 5 月起用的是 setIgnoreMouseEvents(true, { forward: true })，悬浮窗一创建就开着，后来的提醒小窗和锁定功能也靠它。对照 Electron 41 的源码才发现，只要任何一个窗口开了 forward，主进程的 UI 线程上就会装一个 WH_MOUSE_LL 低级鼠标钩子：

从此系统里每一次鼠标移动，都要等这个线程处理完。主线程被垃圾回收或一次同步写盘占住几十毫秒，整台电脑的光标就冻住几十毫秒。macOS 上 forward 只是让这个窗口接收鼠标移动事件，不装全局钩子，所以只在 Windows 上出现。

新做法完全不用 forward：渲染进程把可点区域（我们叫它「洞」）报给主进程，主进程每 50 毫秒读一次光标位置。守卫测试会扫描主进程源码，出现带 forward 的调用就失败。

改的过程中又踩到一个坑：新的轮询每次读两次锁定状态，而 electron-store 的 get() 每次都同步读整个配置文件，锁定期间每秒读盘 40 次，本身就会卡主线程。改成内存缓存后才算完。这个修复 10 月 16 日随 0.33.3 测试版发出，反馈的用户已经装上，效果还在等回复。

05崩溃与恢复：自愈代码也会闯祸

透明窗口的渲染进程死掉时什么都不画，窗口完全隐形。6 月我们加了自愈逻辑：在 render-process-gone 回调里自动 reload()，每分钟最多 3 次。

从 0.25.0 到 0.29.2，Sentry 上一直有一个原生崩溃，大约每天一次，Windows 上报 EXCEPTION_BREAKPOINT。10 月 3 日查清楚了：崩溃就出在这段自愈代码里。

Electron 41.8.0 以前，Chromium 还在遍历「进程死亡」的观察者时，Electron 就发出了 render-process-gone，这时同步 reload() 会撞上 Chromium 的一个断言。上游在 electron/electron#51900 修了它，首个含修复的 41.x 版本是 41.8.0；我们在 package.json 里写的是 ~41.5.1，只会在 41.5.x 里升级，所以一直拿不到。

修法是 reload 用 setTimeout(..., 0) 推迟一个 task，同时升到 41.10.7。验证分三步：独立复现脚本里，41.5.1 同步 reload 第一次崩溃就退出（退出码 133），推迟后不崩；真实应用里连续杀 3 次渲染进程都自动恢复，第 4 次触发上限，应用依然活着；0.29.4 发出后，这个崩溃在 Sentry 上归零。渲染进程本身为什么会挂，还没有解释。

另一个崩溃修不了根因，只能让下次启动更保守。Sentry 上有一台 Windows 11 机器装着 0.30.1，每次启动都崩，7 分钟崩了 11 次，GPU 进程为什么起不来到现在也不知道。Chromium 在 GPU 进程每种模式都崩之后，会主动结束整个浏览器进程。我们加了一个跨启动的降级守卫：

窗口位置恢复也有坑：保存的位置可能在屏幕外，连标题栏都拖不回来。不换显示器也能触发，悬浮窗默认高 660 个逻辑像素。1080p 屏幕开 150% 缩放后逻辑高度只有 720，去掉任务栏，工作区剩 680 左右，和 660 只差 20，保存的位置稍微偏下一点就会超出屏幕。拖动的边界原来按主显示器算，拖不到第二块屏幕上。现在统一按窗口所在显示器（screen.getDisplayMatching）的工作区来限制，先限尺寸，再定位置。

08主线程上的同步读盘，和 490 MB 内存

悬浮窗和游戏同时常驻，空闲开销比峰值性能更重要。主线程上最隐蔽的开销是同步读盘，也就是第四节提到的 electron-store.get() 每次读整个配置文件。它第一次出现是 9 月底：对局中计时提醒加起来每秒读 20 多次，就在处理游戏数据的那条线程上，后来改成读一次、配置变化时失效的缓存。第四节锁定状态那次是第二次。

主线程上的开销改之前改之后
计时提醒读设置每秒 20 多次同步读盘内存缓存，变化时失效
对局战绩写到云端每次游戏数据推送（约每秒 2 次），一局 45 分钟约 5,400 次请求开局一次、之后每 30 秒一次，再加赛后一次
拖动改变悬浮窗大小每一帧同步写一次配置停下 500 毫秒后再写
悬浮窗启动要解析的代码约 1.88 MB（动画库打进了启动代码）约 1.62 MB

这组数字是 0.33.0 在 macOS 上空闲 1 分钟时用活动监视器看的。语音隐藏窗口已改为用到时才创建，macOS 用户和没开语音的 Windows 用户省约 36 MB；懒创建时发给它的命令要排队到页面加载完，否则「检测虚拟声卡」会误报。主窗口隐藏后要不要销毁还没定：按 5 月的估算，留着多占约 40 MB，恢复只要 10 毫秒左右，重建要 1.5 秒。Windows 上和对局中的内存都还没测过。

10自动更新与签名

5 月，0.7.1 自动更新到 0.7.2 失败，提示新版本「is not signed by the application owner」。electron-builder 配置里的 signtoolOptions.publisherName 一个字段管两件事：告诉签名工具写什么名字，也告诉 electron-updater 以后校验新包的发布者。我们的 CI 根本没签名，这个字段却已经写进了用户装好的 0.7.x 的 app-update.yml 里，于是它拒绝了所有没签名的新版本。

删掉这个字段以后，0.7.1 和 0.7.2 的用户只能去官网手动装一次新版：校验配置跟着安装包到了用户手里，后面的更新改不动它。目前两个平台都还没签名，配置文件里留了注释，防止将来买了证书只加回一半。

还有一个和国内用户相关的：退出的代理软件会留下一个失效的系统代理，更新检查因此失败。现在遇到 ERR_PROXY_CONNECTION_FAILED 这类代理错误，就用 session.setProxy({ mode: 'direct' }) 切成直连重试一次，本次运行内保持直连。

12几点心得

症状在像素，病根可能在窗口的合成方式。透明窗口在 Windows 上出问题时，先问一句：是谁改变了这个窗口的合成方式。

Windows 的窗口状态会被别人改掉。置顶层级、任务栏状态、窗口对象本身都可能悄悄变了。每次显示都重新声明一遍，所有入口走同一个「确保存在」的函数。

一个参数背后可能是一个系统级的机制。用到和系统交互的选项时，翻一下它在各平台上的实现，比读 API 文档更能看清代价。

自愈代码要和业务代码一样认真测。在进程死亡的回调里同步做重活，会把「悬浮窗闪一下」变成「整个应用退出」。降级守卫要在崩溃之前写好状态，守卫本身绝不能抛错。

主线程上没有小开销。同步读盘、每帧写配置、高频网络请求，放在一个要和全屏游戏共存的应用里，就是用户能感觉到的卡顿。
